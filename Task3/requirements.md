# Требования к внешним интеграциям «Умный дом»

## 1. Общие требования

Интеграция PropDevelopment с платформой партнёра должна выполняться через отдельный интеграционный слой `Smart Home Integration Gateway`.

Мобильное приложение не должно обращаться к платформе партнёра напрямую. Все запросы должны проходить через backend PropDevelopment.

Основные интеграции:

- PropDevelopment → платформа «Умный дом»;
- платформа «Умный дом» → интеллектуальный домофон;
- платформа «Умный дом» → интеллектуальный шлагбаум;
- платформа «Умный дом» → PropDevelopment для передачи событий.

---

## 2. Требования к безопасности

### 2.1. Защита каналов связи

1. Все внешние соединения должны использовать HTTPS.
2. Минимальная версия TLS — TLS 1.2, предпочтительно TLS 1.3.
3. Необходимо запретить использование незашифрованных HTTP-соединений.
4. Для интеграции с устройствами необходимо использовать защищённые MQTT/HTTPS-соединения.
5. Сертификаты должны проверяться обеими сторонами.
6. При возможности для server-to-server интеграции следует использовать mutual TLS (mTLS).

### 2.2. Защита API

1. API партнёра не должен быть доступен непосредственно из мобильного приложения.
2. Доступ к API должен осуществляться через `Smart Home Integration Gateway`.
3. Необходимо реализовать rate limiting.
4. Должна выполняться валидация входящих запросов.
5. Необходимо защищаться от повторной отправки команд (replay attack).
6. Все команды управления дверью и шлагбаумом должны иметь идентификатор запроса.
7. Для критических операций необходимо вести аудит: пользователь, объект, устройство, время, операция и результат.
8. Секреты интеграции нельзя хранить в исходном коде или конфигурационных файлах в открытом виде.

### 2.3. Защита биометрических данных

Распознавание лица является наиболее чувствительной частью интеграции.

1. PropDevelopment не должна получать и хранить необработанные изображения лиц без необходимости.
2. По возможности биометрическая обработка должна выполняться на стороне платформы партнёра.
3. PropDevelopment должна получать только результат проверки доступа, например:
   - `allowed`;
   - `denied`;
   - идентификатор пользователя/правила доступа;
   - время и устройство.
4. Биометрические шаблоны должны храниться только в системе, ответственной за их обработку, с применением усиленных мер защиты.
5. Доступ к биометрическим данным должен быть строго ограничен.
6. Необходимо определить сроки хранения и процедуру удаления биометрических данных.

### 2.4. Данные об автомобилях

Для интеллектуального шлагбаума необходимо ограничить передаваемые данные.

Рекомендуется использовать:

- идентификатор автомобиля;
- номерной знак или его защищённое представление;
- статус разрешения;
- идентификатор объекта недвижимости;
- срок действия разрешения.

Избыточные данные о перемещениях автомобиля хранить не следует.

## 3. Аутентификация

### 3.1. Мобильное приложение

Для пользователя мобильного приложения рекомендуется использовать:

- OAuth 2.0;
- OpenID Connect (OIDC);
- короткоживущие access token;
- refresh token с контролируемым сроком действия.

Мобильное приложение не должно хранить client secret.

### 3.2. Server-to-server

Для взаимодействия `Smart Home Integration Gateway` с платформой партнёра рекомендуется:

- OAuth 2.0 Client Credentials для машинного взаимодействия;
- mTLS как дополнительный уровень защиты;
- отдельный client ID для каждого окружения;
- отдельные credentials для production и тестовой среды.

### 3.3. Входящие уведомления

Если партнёр отправляет события в PropDevelopment через webhook:

1. webhook должен работать только через HTTPS;
2. источник запроса должен дополнительно проверяться;
3. запрос должен содержать подпись;
4. необходимо использовать timestamp и уникальный event ID для защиты от replay attack;
5. повторная доставка одного события не должна приводить к повторному выполнению команды.

---

## 4. Авторизация

Авторизация должна выполняться не только на уровне API, но и на уровне конкретного объекта недвижимости.

Проверять необходимо:

1. идентификатор пользователя;
2. роль пользователя;
3. объект недвижимости;
4. устройство;
5. тип операции;
6. срок действия разрешения.

Пример:

```text
Пользователь
    ↓
Роль
    ↓
Объект недвижимости
    ↓
Правило доступа
    ↓
Устройство
    ↓
Разрешённая операция
